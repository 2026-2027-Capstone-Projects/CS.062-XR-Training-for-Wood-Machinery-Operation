## Problem and Context
Our project aims to develop an XR training application for operators of industrial woodworking machinery. Written SOPs and instructor demonstrations are important but do not by themselves provide step-by-step interactive practice or immediate feedback. New learners may have difficulty connecting written steps to the physical locations of machine controls, distinguishing procedure states, or recognizing errors. Direct practice on industrial equipment demands supervision and can expose inexperienced users to avoidable risks. The proposed application will provide a safe, simulated, contextual learning environment before formal supervised operation. Our project aims to develop an XR training application for operators of industrial woodworking machinery. 
To support this project, we will simulate a piece of wood machinery in Unity so the user can interact with it in a training environment; to do this, we need to create a 3D model of the machine. We can either use a 3D scanning tool to create our models or hand-model the machine. The project partner encouraged us to use a 3D scanning tool but left the choice up to us. Our team needs to decide which 3D scanning tool we plan to use. 
We need to make this decision so that we can iron out our workflow and begin creating 3D objects to use in Unity. If we don’t decide, we will lose valuable time that could have been spent creating and processing scans for Unity. This also limits our ability to work on the Unity project since we need 3D objects to simulate. This decision is also difficult because if we need to change the tool we use, we will have to rework large parts of our scanning workflow. Depending on the tool, we may have to rescan some objects, spend a large chunk of time cleaning scans manually, and we will also have to spend time learning a different tool. 
## Options
### Option A: [Polycam]
Polycam is a 3D scanning tool that lets users take photos and videos and convert them into a 3D model; it offers free photogrammetry and paywalled Gaussian splatting (“How to Create Photogrammetry and Gaussian Splats”). The software can export files in a usable format for Unity(.obj, .fbx); this feature is paywalled behind a subscription (“What File Types”). This software is easy to use, has a mobile version, and does all model generation in the cloud. The cost is a $30 per month subscription for the features our project needs. (“Pricing | Polycam”) 
### Option B: [RealityScan]
RealityScan is a free 3D scanning tool that lets users take photos, videos, and lidar scans and convert them into a 3D model; it has a mobile version that computes scans in the cloud and a local version that computes them locally. It is relatively easy to use and is also reasonably fast. The benefits are that it is completely free and doesn't require a subscription to export models in the formats we need (.FBX or .OBJ); it is also fairly intuitive, offers more fine-tuned control over model settings, and makes it easier to tell when the pictures provide adequate coverage for a quality scan (“Model Tools”). The cost is that it will be hardware-intensive if we plan to compute scans locally. 
### Option C: [Hand Modeling]
Hand modeling the machine in software such as Blender is an option. This choice, however, will have the highest time cost. This is because none of our teammates are experts in 3D modeling, and it is slightly out of scope of the project; more importantly, it would take the most time not only to model the machine and get that part right but also to texture the model. The benefit of hand modeling is that it would be easier to animate the model since models made by 3D scanning tools tend to be harder to break into the components we need to animate. 
### Option D: Do Nothing
If we don't decide on a 3D scan tool (Do nothing), we will lose time we could've spent grabbing scans of the machine, processing the models, and bringing them into Unity. The only way delaying the decision makes sense is if we do not have access to the machine or if we can get away with using stock assets. 
## Analysis
The trade-offs that matter are quality of scan, how easy it is to get usable video, and how long it takes to generate a scan. My evidence is from personal experience testing out the tools. I tested Polycam on an empty Ultra Paradise Monster can; it was relatively easy to capture enough frames with the mobile app, and it took 20-30 minutes to generate the object in the cloud. The quality was decent; I could read the lettering on the can, but the program clearly struggled with reflective areas, producing artifacts mainly around sharp edges like the can's lip. I then tested RealityScan; I was able to get a similar quality scan using video captured with my phone. The workflow was a little bit more time-consuming since I took the video, transferred it to my laptop, and converted .mov to .mp4 due to Windows codec. I could then import the video into the application. The longest part of the workflow of generating the scan was automatic image masking to separate the object from the environment, which took 20 minutes, and from there it only took a few seconds to generate the mesh and perform texture mapping. The quality was similar: I could read the lettering on the can, and it even seemed to pick up the can's dimpling. What I liked about this program was how much more control I had over the process, such as being able to simplify the mesh as I was running through the workflow instead of having to perform that step afterward; it also had the same issues with artefacting on sharp edges. I am uncertain how much better the object would be if I used lidar captures since we do have access to lidar cameras. One issue we may have with both pieces of software is that, in order to get a good, high-quality scan, we need video/photos around the entire machine with as many different angles as possible, which may not be possible for certain machine components. In this case, we can hand-model certain components we can't get clear, usable footage of. Another consideration is the complexity of the generated mesh. Since our application needs to run in real time on XR hardware, models containing unnecessarily high polygon counts could negatively impact performance (“Configuring Your Unity Project”). RealityScan allows us to simplify the generated meshes before exporting them, which could help reduce this problem (“Model Tools”). However, simplifying a mesh too much may remove important details, especially around controls the user needs to recognize or interact with. Overall, based on my experimentation, both applications have promise. If the convenience of using Polycam is worth the subscription, it is a strong contender; RealityScan is also worth it because we can process and generate the object locally, and hand modeling is a very strong contender in certain situations. I purposely chose an aluminum can for object testing because it's difficult to generate due to the material's reflectivity and the lip's unusual shape, which gives a good idea of what the applications can handle in the worst cases. This, however, may not be representative of what our experience will be scanning the machine. The real machine is a large piece of industrial equipment with flat panels, buttons, and switches. We also will not have access to all angles of the machine, which will limit our ability to make a full scan of the machine. We may be able to get creative with how we scan the machine, but it won't be straightforward. 
## Recommendation and Verification Plan
Based on my testing and analysis, I recommend RealityScan. This is because we can do all model generation locally without relying on cloud computing; it also allows exporting to .obj and .fbx without requiring a subscription. It also provides easy ways for us to tweak model settings, such as polygon counts, without having to fully regenerate the entire model (“Model Tools”).
We will verify the software by generating four models, including components representative of the machinery we intend to simulate, and importing them into Unity. We will evaluate the quality of the geometry and textures, the amount of manual correction required, and whether the model can be used in our training application.
We will consider a model successful if it accurately represents the important visible features of the real object, imports into Unity with its textures intact, and contains no more than 10 minor defects. Minor defects include small geometry artifacts, texture smudging, or other issues that can be corrected without substantially rebuilding the model. Defects will be counted as distinct problem areas rather than individual affected polygons.
We will consider a model unsuccessful if it contains more than 10 minor defects or any major defects that prevent it from representing the object accurately. Critical defects include missing or severely distorted machine controls, large holes in visible geometry, or incorrect representations of components.
If two or more of the four models fail these criteria, we will reevaluate the workflow. We will first determine whether the problems can be corrected by improving image coverage or adjusting settings. If these changes do not resolve the issues, we will consider using Polycam or hand-modeling the affected components before committing to the workflow for the rest of the machine.
If the models pass our criteria, we will then consider the amount of time required to fix and prep each model for use in Unity. We will prep only the models that passed earlier tests because if it has a major defect, it is not worth fixing. This will give us a good picture of how long we should actually expect to spend in a variety of cases, including the worst-case scenario with up to 10 minor defects. This process includes fixing minor defects, breaking components up for animation, and creating animations. Overall, the full process of taking a medium-complexity model with no more than 5 complex features such as buttons and switches, from 3D scanning software to Blender, performing fixes, then putting it in Unity should take at most 3-5 hours to complete. The amount of time models will take to clean and prep should scale with model size, so more complex models will take more time, and less complex models should be fairly quick. This is regardless of physical size since a large flat plane is easier to scan than a small highly detailed button box. If it takes the expected amount of time based on model size, then we will know the workflow will be effective. If not, we will need to reevaluate our 3D scanning software to reduce time-costly defects, and we will also need to reevaluate our 3D modeling software to make sure we are using the most efficient methods for cleaning defects, separating components, and animating where required. And if even after that we are still taking too long to generate final models, then we will need to reevaluate the whole workflow to see if hand modeling the entire machine is a quicker process due to us being able to tailor the entire machine shape to best suit our goals instead of relying on what the 3D scanning software pops out. 
## Constraints
The only licensing constraint is that RealityScan is free for educational purposes, individual use, and companies making less than $ 1 million a year (“Licensing”). PolyCam requires a $30 subscription for the features we need for each user; however, other than that, there are no licensing requirements (“Pricing”). As of writing this document, the project partner has not informed the team of any confidentiality requirements for the machine, or of any intellectual property issues. So, as of right now, we have not been informed of any of these requirements. Licensing constraints for both software, however, may start coming into play if this application is handed off to another company in the future. This, however, has not been disclosed to our team, so as of writing this, it is not an issue.
